→ 목표 15% 경계. 무선 디버깅(첫 측정 18%)이 약 2~3%p 차지.

## 어디서 쓰였나 (`dumpsys batterystats`, 71분)
| 항목 | 값 |
|---|---|
| 화면 켜짐 | 2분 58초 (4%) |
| 커널 `PowerManagerService.WakeLocks` | 1시간 8분 (CPU 가 거의 안 잠듦) |
| 앱 WakeLock `WBM:Monitor` / 오디오 `AudioIn` | 둘 다 모니터링 내내 → **우리 WakeLock 은 사실상 중복** (녹음 중엔 오디오 시스템이 잡음) |
| **앱 CPU 시간** | **user 36분 55초 + system 11분 5초 ≈ 48분 / 71분** |

### 스레드별 CPU (프로세스 시작 22:41 이후, `top -H`)
| 스레드 | CPU |
|---|---|
| **메인(UI) 스레드** | **24분** |
| HeapTaskDaemon (GC) | 3분 7초 |
| Jit | 1분 57초 |
| DefaultDispatcher ×3 (오디오·엔진·동기화) | 약 3분 33초 |
| RenderThread | 32초 |

- **오디오 처리 자체는 작다(약 3.5분). 화면이 거의 꺼져 있었는데 메인 스레드가 24분을 썼다** → UI 쪽 낭비가 주범으로 보임
- 화면 켜고 앱이 맨 앞일 때 순간 측정은 약 1.8% — 화면 꺼진 상태에서 무엇이 메인 스레드를 쓰는지 **아직 확정 못 함**
  (비교 측정 중 모니터링이 꺼져 있었고, 이어서 워치가 offline 이 되어 중단)

## 의심 가는 곳 (다음에 확인·수정)
1. 워치 `WearApp` 이 `collectAsState` 로 엔진 상태(100ms 마다 dB 변경)를 **생명주기와 무관하게** 계속 받음 → 화면이 꺼져도 초당 10번 상태 갱신·재구성 예약, `SimpleDateFormat` 등 할당 → GC
   → `collectAsStateWithLifecycle` 로 바꾸고, 화면 표시용 레벨은 4Hz 정도로 줄이기
2. `SensorState` 에 dB 가 들어 있어 **상태 전체가 100ms 마다 바뀜** → StatusHub·HistoryRecorder·설정 저장 수집기가 모두 10Hz 로 깨어남
   → 레벨을 별도 StateFlow 로 분리
3. 앱 WakeLock `WBM:Monitor` 는 녹음 중 `AudioIn` 과 겹침 → 유지 여부 재검토 (CLAUDE.md §4-6 결정이라 ADR 필요)
4. 다음 측정은 두 조건을 나눠서: 화면 꺼짐 + 앱 맨 앞 / 화면 꺼짐 + 앱 백그라운드 (각 60초, `/proc/<pid>/stat`)
