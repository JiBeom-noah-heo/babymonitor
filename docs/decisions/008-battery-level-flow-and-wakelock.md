# 008. 배터리: 레벨 흐름 분리, 화면 수집 생명주기, WakeLock 유지

- 날짜: 2026-10-01
- 상태: 채택 (효과는 재측정으로 확인 예정)

## 배경 (devlog 2026-09-30 배터리 재측정)
시나리오 A 알림 모드에서 워치 소모 약 16%/시간 (무선 디버깅 끈 구간 약 14.7%) — 목표 15% 경계.
`dumpsys batterystats` (71분):
- 화면 켜짐 3분뿐인데 **앱 CPU 48분**, 그중 **메인(UI) 스레드 24분**, GC 3분
- 오디오 처리(코루틴 스레드)는 약 3.5분
- 앱 WakeLock `WBM:Monitor` 와 오디오 시스템 `AudioIn` 이 **같은 시간** 잡힘 → 커널 WakeLock 시간은 둘이 겹친 그대로

## 결정
### 1. 레벨(dB)을 `SensorState` 에서 분리 → `SensorEngine.level`
- `SensorState` 는 이벤트가 있을 때만 바뀐다 (시작·정지, 알림, 설정, 스트리밍, 오류, 마이크 막힘)
- 이전에는 100ms 마다 상태 전체가 바뀌어 `/status` 발행·기록·설정 저장 수집기가 **초당 10번** 깨어났다

### 2. 화면은 보일 때만 수집, 표시 간격 250ms
- 워치 `collectAsState` → `collectAsStateWithLifecycle` (화면이 꺼지거나 앱이 뒤로 가면 수집 중단)
- 레벨 숫자·바는 `sample(250ms)` (`Constants.Audio.UI_LEVEL_INTERVAL_MS`). 판정은 100ms 그대로
- 폰 감지기 화면도 같은 방식 (ViewModel `WhileSubscribed`)

### 3. 앱 WakeLock(`WBM:Monitor`)은 유지 (CLAUDE.md §4-6)
- 녹음 중에는 오디오 시스템이 `AudioIn` 을 잡으므로 **빼도 줄어드는 배터리가 사실상 0** (측정상 겹침)
- 반대로 오디오가 잠깐 멈추는 경우(장치 전환, 다른 앱의 마이크 점유 등)에 생존 신호·판정 코루틴이 멈출 위험
- → 유지. 1시간 상한·30분 갱신(밤샘 안전)은 그대로

## 확인 방법
- 같은 조건 1시간 재측정 + batterystats: 앱 CPU 시간, 메인 스레드 시간이 줄었는지
- 화면 꺼짐 + 앱 맨 앞 / 화면 꺼짐 + 앱 백그라운드 각 60초 CPU (`/proc/<pid>/stat`)

## 대안
- **레벨 판정 주기 늘리기(100ms → 200ms)**: 판정 로직·테스트 전체가 100ms 기준이고, 측정상 오디오 처리는 주범이 아님 → 보류
- **WakeLock 제거**: 위 3 의 이유로 보류
